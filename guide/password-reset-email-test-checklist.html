密码重置邮件怎么测？链接过期、一次性与重复请求的测试清单

“忘记密码”是最容易被忽略、出了问题却最伤用户的流程之一：邮件没到、链接用两次还有效、过期了没提示。这篇清单把密码重置邮件拆成可执行的测试用例，并说明怎样用独立的临时邮箱接收和核对每一封。

01

密码重置为什么要单独测

重置邮件连着账户安全：链接泄漏或永不过期，就等于给账户留了后门；邮件迟迟不到，用户则被锁在门外。它又和注册验证不同：账户已存在，要考虑重复请求、旧链接失效、会话处理等状态变化。

如果你还没有注册阶段的用例，可以先看注册验证邮件测试用例清单，两份清单可以共用同一套测试地址策略。

02

测试前：准备独立的收件地址

密码重置必须对已存在的账户发起，所以测试前先用一个全新的地址注册并验证账户。CleanTempMail 的网页收件箱免费、无需注册，可以生成随机地址，也支持自定义前缀；把用例编号写进前缀（例如 reset-001），结果表与收件箱就能一一对应。

一个用例用一个地址，不要在多个用例之间复用，否则上一次的重置邮件会干扰这一次的判断。并行执行时的隔离方法见给每个用例一个独立临时邮箱。

03

八个核心用例与应有的断言

密码重置邮件测试用例
场景操作应断言
正常重置对已验证账户点击“忘记密码”邮件到达；收件人正确；链接指向你的测试环境，而不是生产环境
链接可用点击链接并设置新密码能打开重置页；新密码可登录，旧密码失效
一次性使用成功重置后再次点击同一链接被拒绝，并有明确提示，而不是再次进入重置页
链接过期等到有效期之后再使用链接被拒绝；提示用户重新申请，页面不暴露技术细节
重复请求连续申请两次重置行为符合设计：只有最新链接有效，或两个都有效，规则要明确并保持一致
不存在的账户输入一个从未注册的地址页面提示不泄露该账户是否存在；不应发出重置邮件
频繁请求短时间内多次提交有频率限制或冷却提示，不会无限制发信
邮件内容打开正文占位符已替换；无乱码；不包含明文密码；有“不是我本人操作”的说明

有效期、冷却时间这类数字应以你的产品设计为准，用例里写“符合设计”并附上具体数值，而不是照搬别处的经验值。

04

手工测试的四个步骤

  1. 建立账户。用测试地址注册并完成验证，记下提交时间。
  2. 触发重置。在被测应用里申请重置，然后回到网页收件箱，用自动或手动刷新查看邮件。
  3. 核对邮件。打开正文，检查收件人、主题、链接域名与说明文字；CleanTempMail 的收件箱会屏蔽邮件中的外部图片，所以这里主要核对文字和链接。
  4. 走完并清理。完成重置后再验证一次性与过期等用例，最后用“删除”或“清空”移除邮件，避免残留可用的重置链接。

邮件迟迟未到时，先别急着提 bug，按收不到邮件的排查步骤区分是发送端、地址还是收件箱的问题。

05

要自动化时的注意点

回归频繁时可以把上述流程写进自动化。CleanTempMail 的付费 REST API 可以读取邮件，具体接口以官方文档为准。设计上记住三点：

  • 等待要有上限。按固定间隔轮询，到点就失败并输出地址和阶段，不要无限重试。
  • 按地址与主题匹配。只认属于本次运行的那一封，而不是“最新一封”。
  • 轮询会计入额度。官网说明受保护的请求每次都计数，包括返回空结果的轮询，所以间隔不要太密。

轮询与额度的具体算法见API 自动化测试指南。共享试用密钥只适合体验，持续测试请用自己的独立密钥，并放进 CI 的密钥配置。

06

别踩的坑

  • 日志里留下完整链接。重置链接等同于临时密码，报告里只保留脱敏片段。
  • 用真实用户的邮箱测试。用专用的测试地址，避免给真实用户发信。
  • 邮件只是暂存。官网的隐私与安全说明指出邮件是临时的、不会被永久存储，需要作为证据的截图请在测试期间保存。
只测试自己的系统

这些用例用于你自己的产品或已获授权的环境。不要对第三方网站的账户发起大量重置请求。

07

常见问题

密码重置链接应该多久过期？

没有统一答案，取决于你的产品安全设计。测试的重点是：过期后必须被拒绝，并提示用户重新申请；具体时长以需求文档为准。

为什么不存在的账户不应提示“该邮箱未注册”？

明确提示会让他人探测哪些邮箱已注册。常见做法是对所有输入给出相同的中性提示，只给真实账户发邮件。具体策略以你的产品设计为准。

重置邮件测试需要用 API 吗？

不一定。手工回归用网页收件箱就够了；用例需要频繁自动运行时，再考虑付费 API。

测试要用已注册的账户吗？

是的，重置流程针对已存在的账户。先用独立的测试地址注册并验证，再发起重置。

收件箱里的重置邮件会一直保存吗？

不会。官网说明邮件是临时的、不会被永久存储，需要保留的证据请在测试期间另存。
