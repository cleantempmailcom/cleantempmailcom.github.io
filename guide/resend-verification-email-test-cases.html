“重新发送验证邮件”怎么测？重发、冷却时间与旧链接失效的测试清单

注册流程里的“没收到？重新发送”按钮很容易被漏测：点了之后到底发了几封？旧的链接还能用吗？连点十次会怎样？这篇给出一份可直接照着跑的测试清单，并说明如何用独立的临时收件箱把每次重发都看得清清楚楚。

01

准备：每个用例一个独立地址

重发测试要数“收到几封”，所以收件箱必须干净。每个用例使用独立地址，否则别的用例的邮件会混进计数。CleanTempMail 的网页收件箱免费、无需注册，可以用随机前缀，也可以自定义前缀，比如把用例编号写进去，方便对应。并行跑测试时的做法见给每个用例一个独立临时邮箱。

手动测试时，直接在 CleanTempMail 打开收件箱，用自动或手动刷新观察新邮件，展开正文查看链接，用完可以删除或清空。

02

核心测试用例

  1. 重发确实发出新邮件：注册后先不点链接，点“重新发送”，收件箱应出现新邮件，并记录收到时间。
  2. 冷却时间：如果产品设计了倒计时，在倒计时内按钮应不可用或给出提示；倒计时结束后再点应成功。
  3. 连续快速点击：短时间内连点，预期要么只发一封，要么按产品规则限流，而不是一次发出一堆邮件。
  4. 旧链接是否失效：按产品规则确认。若设计为“新链接生效，旧链接作废”，用旧链接访问应得到明确的失效提示，而不是静默成功或报错页。
  5. 新链接可用且只能用一次：点击新链接完成验证后，再次点击应提示已验证或已使用。
  6. 已验证账号再点重发：应有合理提示，不应再发验证邮件。
  7. 填错邮箱后修改地址再重发：邮件应发到新地址，旧地址的收件箱不应再收到。可用两个临时邮箱对照检查。

注册验证本身的完整用例见注册验证邮件测试用例清单，密码重置场景见密码重置邮件测试清单。

03

别把“还没到”当成“没发”

邮件到达有延迟。自动化里应设定轮询间隔和超时，而不是写死 sleep；超时才判失败。注意一个常见错误：断言“没有收到第二封”时，如果只等了一瞬间，即使系统有 bug 也会通过。给“不应出现”的断言也留出同样的等待窗口。若超时后仍然没有邮件，用收不到邮件的排查指南区分是发送端、地址还是收件箱的问题。

04

需要批量跑时用 API

手动点几次没问题，放进 CI 就要自动化。CleanTempMail 提供付费 REST API，包含一次性购买的密钥套餐（Starter 10k 次 $3，Growth 50k 次 $12，Pro 200k 次 $39，Business 1M 次 $149），也有共享的 ct-test 试用密钥。注意每次轮询都会计入次数，包括返回空结果的轮询，所以重发用例要把轮询间隔和超时控制好。接口细节以官方文档为准，更完整的流程见邮件测试 API 指南。

05

记录什么，才能复现问题

  • 每次点击重发的时间和收到邮件的时间。
  • 收到的邮件数量，以及每封邮件链接是否不同。
  • 旧链接、新链接的访问结果。
  • 日志里不要写出完整验证码或带凭证的链接。
06

常见问题

重发验证邮件应该一次发几封？

由产品规则决定。通常点一次发一封，并受冷却时间或频率限制约束；测试时以需求文档为准。

旧验证链接一定要失效吗？

不一定，取决于产品设计。关键是行为要明确、一致，并写进用例。

临时邮箱适合测重发吗？

适合。每个用例一个干净的收件箱，数邮件数量很直观。

网页收件箱需要注册吗？

不需要，免费使用，打开即可创建地址。

API 轮询空结果算次数吗？

算。每次轮询都计入次数，包括空结果，所以要设定间隔和超时。
