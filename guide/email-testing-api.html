临时邮箱 API 自动化测试：轮询、断言与额度规划

一个可靠的邮件测试，应该能解释失败发生在发送、等待还是内容验证阶段。这份指南给出测试设计与请求预算示例，帮助你把邮件检查加入自己的回归流程。

01

先让每次测试有独立的标识

为本次运行生成唯一标识，把它写入测试地址前缀或邮件主题。并发任务不能只依据“列表里有一封邮件”判断成功，否则可能读到另一个测试留下的消息。

正式接入时从 官方 Quickstart 确认当前域名与地址流程。生成器是可选的；官方也说明可以在有效域名上本地组合地址。这两种选择的请求预算不同。

02

把等待写成有上限的状态机

邮件可能不会在触发发送的同一瞬间出现。给轮询设置间隔和截止时间，每次只检查属于这次运行的消息。发生接口错误时，记录阶段和状态码，再根据文档决定有限重试或终止。

# 流程伪代码，不是可直接执行的 SDK
run_id = unique_id()
address = prepare_test_address(run_id)
trigger_your_app_email(address)
deadline = now() + wait_budget
while now() < deadline:
    messages = list_inbox(address)
    match = find_message(messages, run_id)
    if match:
        inspect_and_assert(match)
        cleanup_test_message(match)
        return success
    sleep(poll_interval)
return delivery_timeout

伪代码故意把具体端点、字段与错误映射留给当前官方接口。不要把空列表当作成功，也不要因为持续等待而无限重试。

到达等待上限后，可按收不到邮件的排查指南区分发送、地址、投递与收件箱问题，避免只增加重试次数。

03

断言消息是否属于当前流程

  • 核对收件人、运行 ID 与预期主题。
  • 检查正文中本次流程需要的字段，而不是只检查“有文本”。
  • 验证链接的主机名是否属于你的测试应用，再按测试目的处理链接。
  • 对验证码检查格式和所属流程，避免混用其他测试的代码。
  • 需要验证附件时，明确检查名称、类型或内容，并计入额外请求。

给失败报告记录步骤、耗时和脱敏后的断言差异。避免记录密钥、完整验证码或带访问凭据的链接。

04

给轮询次数与额外操作分别计数

受保护 API 的每次轮询都会消耗请求额度，包括空收件箱。下面采用可选生成器、一次正文读取和一次邮件删除作为三次基础操作；本地组合地址时，生成器的那一次不需要计入。

这里假设按间隔查询、到达上限即停止；如果加入立即查询、重试、正文多次读取或附件下载，必须相应增加预算。消息提前到达并结束轮询时，实际次数可能更少。

可以在 首页额度估算器 调整次数与间隔；计费细节仍以官方 API 文档为准。

05

在 CI 中准备密钥、清理与失败报告

将独立密钥放入 CI 的秘密配置，在受控的服务端任务中使用，不写入网页、公开仓库、查询参数或日志。共享测试密钥不适合依赖稳定额度的持续测试。

清理阶段也需要报告结果。若断言失败后执行清理，先保存脱敏的测试证据；若清理失败，将其作为独立状态记录，避免把送达成功与清理成功混为一谈。

可从一条欢迎邮件流程开始，再扩展到密码重置或附件测试。可以把相同的运行标识和阶段报告用于更多通知类型，让失败更容易定位。
