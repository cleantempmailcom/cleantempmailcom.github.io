注册验证邮件怎么测？QA 测试用例清单与临时邮箱用法

01

为什么验证邮件值得单独设计用例

验证邮件把“注册成功”和“账户可用”连在一起。它没到达、链接打不开或验证码填不进去，用户通常就此流失，而且后台的接口监控未必报错。

手工测试时，很多团队反复使用同一个个人邮箱：旧邮件混在一起，分不清哪封属于这次测试，也很难复现“新用户第一次收到什么”。给每个用例一个全新的地址，是最直接的隔离办法。

02

用独立地址隔离每个用例

CleanTempMail 的网页收件箱免费，无需注册，可以生成随机地址，也支持自定义前缀。手工测试时可以这样安排：

  1. 用例编号写进自定义前缀，例如 reg-001、reset-002，结果表里的编号与收件箱一一对应。若该前缀已被占用，改用随机地址即可。
  2. 需要多个域名的场景（例如检查域名白名单或黑名单规则），在官网当前可用的域名中切换，具体以官网实时列表为准。
  3. 需要用到你自己的域名时，按官方指引把 MX 记录指向 mail.cleantempmail.com，详见自有域名临时邮箱配置指南。
  4. 需要让同事一起查看结果时，用“复制链接”分享直达收件箱的链接，注意它等同于进入收件箱的凭据。

需要把检查写进自动化流程时，再参考API 自动化测试指南；手工用例阶段，网页收件箱已经足够。

03

八类核心测试用例

注册与账户邮件的测试用例
场景操作应断言
首次注册用全新地址提交注册邮件到达；收件人正确；主题与品牌名符合预期
验证链接点击邮件中的按钮跳转到你的域名；账户状态变为已验证
验证码复制验证码填入表单格式与位数正确；输入后可通过
重发验证邮件点击“重新发送”收到新邮件；旧链接按产品规则失效或仍有效，行为明确
重复注册用同一地址再次注册提示合理，不泄露多余账户信息，不产生重复账户
密码重置对已验证账户发起重置重置邮件到达；链接可用一次后的行为符合设计
邮件内容查看正文与附件（如有）占位符已替换；无乱码；附件名称和类型正确
延迟与超时记录发送到收到的时间耗时在你的预期范围内；超时有可见提示

前五行关注流程是否畅通，后三行关注细节质量。刚开始时，先把“首次注册”和“验证链接”做扎实，再逐步补齐其余场景。

04

把每次测试留成可复现的证据

邮件问题经常无法复现，因为现场没有保留下来。建议每个失败用例至少记录：

  • 使用的测试地址（不含任何敏感信息）和提交表单的大致时间。
  • 收件箱当时的状态：是否出现邮件、收到的主题、发件人。
  • 验证链接的目标域名是否为预期的测试环境，而不是生产环境。
  • 截图或脱敏后的正文片段；不要保存完整验证码或带访问凭据的链接。

如果预期的邮件始终没有出现，先对照收不到邮件的排查步骤，区分是发送端、地址问题还是收件箱本身的问题，再决定是否提 bug。

05

常见陷阱

  • 测试环境链接指向生产：邮件模板里的域名在不同环境不一致，是最常见的缺陷之一。
  • 重复使用同一地址：上一次的邮件会干扰这一次的判断，请为每个用例换新地址。
  • 只验证“邮件到了”：还要点开链接、输入验证码，验证流程真正走通。
  • 邮件客户端差异：收件箱网页能看到的内容，不等于所有客户端的渲染效果；排版类问题需另行检查。
遵守服务规则

只在你自己的产品和测试环境里做这类测试。对第三方网站，请遵守对方对临时邮箱和自动化访问的规定。

06

测试结束后的清理

用“删除”移除单封邮件，或用“清空”一次清空收件箱，避免残留的验证码和重置链接留在可直达的地址里。官网的隐私与安全说明指出，邮件都是临时的、不会被永久存储，需要作为证据保留的内容，请在测试期间自行保存。

07

常见问题

做注册测试，一定要用 API 吗？

不一定。手工回归用网页收件箱就够了；当用例需要频繁、自动地运行时，再考虑付费 API。

为什么每个用例要换新地址？

这样收件箱里只有当前用例产生的邮件，断言更准确，失败时也更容易定位。

可以用自己的域名做测试吗？

可以。按官方指引把域名的 MX 记录指向 mail.cleantempmail.com，再按配置指南验证。

测试用的临时地址能保留多久？

官网说明邮件是临时的、不会被永久存储，请不要把它当作长期档案，需要保留的证据请及时另存。

线上第三方服务可以用这套用例吗？

请只测试你自己的产品。第三方服务有各自的使用规则，应当遵守。
