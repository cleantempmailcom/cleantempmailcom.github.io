预发布环境的测试邮件怎么管？别再让测试数据发给真实用户

测试环境里最危险的一类 bug，是“功能没问题，邮件却发给了真实用户”：用生产数据库的副本跑预发布，触发一次批量通知，客户就收到了一封写着 TEST 的邮件。这篇文章讲怎样管理测试环境的收件人，让所有测试邮件都落在你控制的收件箱里。

01

测试邮件误发是怎么发生的

常见路径有三种：测试库里混入了真实用户邮箱；测试账号用的是同事或自己的私人邮箱，邮件散落各处；预发布环境的邮件开关没有关，和生产共用同一套发送配置。

解决思路只有一个：测试环境里出现的每一个收件地址，都应该是为测试专门准备、并且你能看到内容的地址。

02

测试收件人的四条规则

  • 只用专用地址：测试账号一律使用测试专用邮箱，不使用真实用户或个人邮箱。
  • 一次一址：每个测试用例或每次运行用独立地址，避免互相串信，原理见并行测试的独立收件箱。
  • 环境开关：在预发布环境的发信逻辑里加白名单或拦截，只允许发往测试域名或测试地址。
  • 数据脱敏：从生产复制数据时，替换掉所有邮箱字段。
03

五步落地

  1. 盘点发信入口：列出注册、重置密码、通知、营销等所有会发邮件的功能。
  2. 准备测试地址：在 CleanTempMail 网页收件箱可免费生成地址，无需注册，支持随机或自定义前缀，比如用环境名加用例名，一眼就能认出。
  3. 在预发布环境触发：用这些地址走一遍流程。
  4. 在收件箱核对：手动或自动刷新，打开邮件正文，检查主题、链接域名是否指向测试环境，而不是生产。
  5. 清理：核对完删除邮件或清空收件箱。如需被自动化脚本调用，CleanTempMail 另有付费 REST API，详见临时邮箱 API 测试指南。
04

上线前的检查清单

  • 邮件里的链接指向预发布域名，而不是生产域名。
  • 主题或正文能看出是测试环境，方便与真实邮件区分。
  • 不同环境的发信配置相互独立。
  • 测试数据里没有真实用户邮箱。
  • 邮件正文里的外部图片加载情况符合预期。CleanTempMail 的追踪保护会阻止外部图片加载，所以如果要检查图片，请在其他渠道另行确认。
05

什么时候不适合用临时邮箱

需要长期保留的测试账号，比如要持续几周接收通知的集成测试，或需要长期稳定查看历史邮件的场景，不适合使用临时地址。CleanTempMail 的邮件是临时的，不会永久保存。这类需求可以考虑自有域名收信，参见自定义域名临时邮箱。

06

常见问题

预发布环境可以用临时邮箱吗？

可以，用于短期核对注册、重置密码等邮件。需要长期保留历史邮件的场景不适合。

需要注册 CleanTempMail 吗？

网页收件箱免费，无需注册。

测试邮件会一直保留吗？

不会。邮件是临时的，不会永久保存，需要留存的内容请自行另存。

自动化脚本能用吗？

可以使用付费 REST API，详见 API 测试指南和官方文档。

可以用自己的域名吗？

可以，通过 MX 记录指向 mail.cleantempmail.com 即可使用自定义域名。
