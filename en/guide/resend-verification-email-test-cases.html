How to Test a “Resend Verification Email” Button: Cooldowns, Old Links and Repeat Requests

The “Didn’t get it? Resend” button in sign-up flows is easy to skip in testing: how many emails does one click send? Does the old link still work? What happens after ten clicks? Here is a checklist you can run as is, plus how a separate temporary inbox makes every resend visible.

01

Setup: one separate address per test case

Resend tests count how many messages arrive, so the inbox must be clean. Use one address per case, or other cases’ emails will pollute the count. The CleanTempMail web inbox is free with no sign-up, and supports random or custom prefixes, so you can put the case ID in the prefix. For parallel runs, see one temporary inbox per test case.

For manual testing, open CleanTempMail, use auto or manual refresh to watch for new mail, open the body to inspect the link, and delete or clear when done.

02

Core test cases

  1. Resend really sends a new email: sign up, do not click the link, press “Resend”; a new message should appear. Note the time.
  2. Cooldown: if the product has a countdown, the button should be disabled or show a notice during it, and work after it ends.
  3. Rapid clicks: expect either one email or throttling per product rules, not a burst of messages.
  4. Old link behavior: follow the product rule. If the new link supersedes the old one, the old link should show a clear invalid message, not silently succeed or hit an error page.
  5. New link works once: after verifying, clicking again should say already verified or used.
  6. Resend on a verified account: a sensible message, and no new verification email.
  7. Fix a typo’d address, then resend: mail goes to the new address and the old inbox gets nothing more. Use two temporary inboxes to compare.

For the full sign-up set see the verification email test cases, and for resets the password reset checklist.

03

Do not mistake “not yet” for “not sent”

Delivery has latency. In automation, use a poll interval and deadline instead of a fixed sleep, and fail only on timeout. A common mistake: asserting “no second email” after waiting a split second passes even with a bug. Give “should not appear” assertions the same wait window. If nothing arrives by the deadline, use the missing email troubleshooting guide to separate sender, address and inbox issues.

05

What to record so you can reproduce

  • Time of each resend click and each arrival.
  • Number of emails received, and whether links differ.
  • Result of visiting the old and new links.
  • Never log full codes or credential-bearing links.
06

Frequently asked questions

How many emails should one resend send?

That is a product rule. Usually one per click, subject to cooldown or rate limits; follow your requirements.

Must the old verification link expire?

Not necessarily. It depends on the design; what matters is that the behavior is clear, consistent and written into the case.

Is a temporary inbox good for resend tests?

Yes. One clean inbox per case makes counting emails straightforward.

Does the web inbox need sign-up?

No. It is free and you can create an address right away.

Do empty API polls count?

Yes. Every poll counts, including empty results, so set an interval and a deadline.
