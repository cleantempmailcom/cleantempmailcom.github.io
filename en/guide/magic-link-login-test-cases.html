How to Test Magic Link Login: A Test Case Checklist for Email Sign-In

Magic link login swaps the password for a link in an email. That removes the password but puts all the testing weight on the email: does it arrive, is the link right, and what happens on expiry or a second click. Here is a checklist you can run as is.

Setup: one inbox per test case

Cross-talk is the main risk: two cases sharing one address can click each other’s link. Give every case its own address. CleanTempMail’s web inbox is free with no sign-up; use a custom prefix (case ID plus timestamp, say) or a random address. It refreshes automatically or manually and shows the message body. For parallel runs see one temporary inbox per test case.

02

Happy path cases

  • Request a link: submit the address and see a “sent” message, and check whether it avoids revealing if the address is registered (per your product rules).
  • Email content: open the message and check sender name, subject, and that the link domain matches the environment, so staging never sends production links.
  • Click to sign in: the link should land on a signed-in state and the right page.
  • First-time user: if the product creates accounts automatically, confirm the account state after the first click.
03

Expiry and single use

  • Expiry: clicking after the validity window should show an expired message and a way to request a new one, not fail silently.
  • Single use: a second click on the same link should be rejected, if that is your design.
  • Repeated requests: request twice and check whether the older link stops working, matching your rules. The thinking is the same as in resend verification email test cases.
04

Edge cases and other devices

  • Open in another browser or device: see whether the product allows it or requires the same device.
  • Click while signed in: an existing session plus a new link should have a clear result.
  • Truncated or altered link: a modified token should be rejected safely without leaking information.
  • Case and whitespace in the address: uppercase letters or surrounding spaces should behave consistently.
  • Images in the email: CleanTempMail’s tracking protection blocks external images, so reading mail there confirms the login flow does not depend on them.
05

Automation: wait for the email, do not hard-code a sleep

In automated tests, poll the inbox with a timeout and extract the link once the message arrives instead of sleeping a fixed time. CleanTempMail offers a paid REST API for reading mail programmatically; see the email testing API guide. For stable waiting patterns read why verification email tests are flaky.

06

Frequently asked questions

Do I need a real mailbox to test magic links?

No. A separate temporary inbox is enough as long as you can receive the message and read its body and link.

How do I avoid clicking another test’s link?

Use a separate address per case, for example a custom prefix containing the case ID.

How long should a link stay valid?

That depends on your product design. The test confirms the actual behavior matches it.

Do I need to register for CleanTempMail?

No. The web inbox is free with no sign-up.
