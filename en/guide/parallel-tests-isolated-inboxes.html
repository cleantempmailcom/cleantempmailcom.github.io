Parallel tests keep reading the wrong verification email? Give each test its own inbox

Once tests run in parallel, a shared inbox becomes a liability: test A reads test B’s code, and a rerun passes. The cause is not slow mail, it is missing isolation. This guide gives each test its own address and keeps API requests within budget.

Why a shared inbox makes parallel tests flaky

The typical symptom: stable locally in serial, occasionally red in parallel CI. Several tests register with the same address and each takes “the latest email”, which may belong to another test. Retries help only because timing shifts.

Longer waits do not fix this. For waiting strategy see reliable waiting for verification email in E2E tests; this guide handles the earlier step: ensuring each test can only see its own mail.

02

The rule: one test, one address, one run ID

  • Unique address. CleanTempMail supports random or custom prefixes. Build the prefix from a run number plus the test name so failures are easy to trace.
  • No reuse. Do not reuse an address across tests or retries, or old mail pollutes assertions.
  • Specific assertions. Do not just check that mail arrived; check the recipient, subject and the code or link in the body.

To keep test traffic on your own domain, see the custom domain guide: point MX at mail.cleantempmail.com.

03

Four steps to implement it

  1. Generate a unique address. At the start of each test, combine the run number and a random suffix into a prefix.
  2. Register with it. Give the address to the app under test and trigger the verification email.
  3. Poll with limits. Set a total timeout and fixed interval, read only that address, and on timeout fail and print the address for debugging.
  4. Assert and clean up. Extract the code or link, assert, then delete the message or clear the inbox.

The paid CleanTempMail REST API can create addresses, read mail, download attachments and delete messages, which suits automating these steps. For polling and assertion design see the temporary email API testing guide.

04

Put request counts in your budget

API usage is counted per request, and protected requests count after authentication, including polls that return empty results. Many parallel tests with short intervals multiply consumption.

  • Keep intervals reasonable and cap the number of polls.
  • Have each test read only its own address instead of scanning everything.

05

Limits to know about

Mail in a temporary inbox is temporary and not stored permanently, so save any evidence you need (a screenshot, the code) into your test report once assertions finish. Test only your own application or an environment you are authorized to use; do not mass-register on third-party services.

06

Frequently asked questions

Can parallel tests share one temporary inbox?

Not recommended. Tests read each other’s mail and fail intermittently. One address per test is more stable.

Can I choose a custom address prefix?

Yes, random or custom prefixes are supported, so you can put the run ID in the address.

Do empty polls use API requests?

Yes. Protected requests count after authentication, including empty results and repeated polling, so set an interval and a cap.

Can I debug in the web inbox?

Yes. The web inbox is free and needs no registration; open the failing test’s address to see its mail.

Is test mail kept forever?

No. Mail in a temporary inbox is temporary and not stored permanently.
