How to Test Email Verification Codes in Cypress with cy.task and a Temporary Inbox

Cypress specs run in the browser, so they are a poor place to carry an API key, and Cypress has no built-in mailbox. To test “sign up, receive a code, type it back in”, the usual structure is to hand the mail lookup to cy.task in Node. This guide shows that structure, what to watch at each step, and how to keep tests from interfering with each other.

Why fetch mail through cy.task in Cypress

Cypress specs run in the browser, while reading mail needs a server-side call with a key. Putting that key into spec code or browser-visible config is unsafe. cy.task runs in the Node process, so it can own the “look in the inbox” step and give the spec only the result.

CleanTempMail’s web inbox is free and needs no sign-up, good for manual checks; reading mail from code needs the paid REST API. The sketch below assumes no endpoint path or field, so write your adapter from the official API Quickstart.

02

Step 1: one unique address per test

Generate a unique prefix in the test from a timestamp and a random number, such as cy-login- plus a random string. Parallel runs and retries then never read another test’s mail. The reasoning is in isolated inboxes for parallel tests; if you need to control the domain, see the custom domain guide.

03

Step 2: write the lookup as cy.task with bounded polling

This is illustrative code; the structure matters, not the API details:

// cypress.config.js (illustrative: fetchMessages is an adapter you write from the official API docs)
const { defineConfig } = require('cypress');
const { fetchMessages } = require('./support/mail-adapter');

module.exports = defineConfig({
  e2e: {
    setupNodeEvents(on) {
      on('task', {
        async getEmail({ address }) {
          const msgs = await fetchMessages(address); // runs in Node; the key lives only here
          return msgs.length ? msgs[0] : null;       // null means "not yet"
        },
      });
    },
  },
});

// spec
const address = `cy-login-${Date.now()}-${Cypress._.random(1e4)}@your-domain`;
cy.visit('/login');
cy.get('[name=email]').type(address);
cy.contains('button', 'Send code').click();
function waitForMail(n = 0) {
  if (n > 15) throw new Error('timeout: no email received');
  return cy.task('getEmail', { address }).then((m) => m || cy.wait(4000).then(() => waitForMail(n + 1)));
}
waitForMail().then((m) => { /* assert recipient and subject, extract the code */ });

Key points: the task returns null for “not yet”, which is never a pass; the number of polls and the interval have a hard limit (about 60 seconds here); a timeout throws a clear error. Avoid a fixed cy.wait(10000) in place of polling: it is either too short and flaky or too long and slow.

04

Step 3: assert the mail belongs to this test

  • The recipient equals the unique address generated for this test.
  • Subject or sender match expectations; “a message exists” is not enough.
  • The code has the right length and characters before it goes in the form.
  • A link’s hostname belongs to your test environment before you visit it.

For resend, duplicate signup and more, see the verification email test-case checklist.

05

Step 4: before moving to CI

Keep the key in CI secret configuration and use it only in the Node-side task; never in the repository, query strings or logs. The shared trial key on the site is for trying things out, not a dependable quota for ongoing tests. With the paid API every poll counts toward quota, empty results included, so do not set intervals too tight.

On failure, save redacted evidence first (the address used, time waited, how many messages the last poll returned), then clean up. Use this only on your own product and test environments, and follow third-party sites’ rules.

Frequently asked questions

Can a Cypress spec read email directly?

Not safely. Reading mail needs a keyed call; run it in cy.task on the Node side so the spec only receives the result.

Is a fixed cy.wait good enough?

No. A fixed wait is either too short and flaky or too long and slow; bounded polling continues as soon as the mail arrives.

Does polling use quota?

With the paid API, yes. Empty polls count too, so set sensible intervals and a limit.

Can I use the web inbox for manual checks?

Yes. It is free and needs no sign-up; use the official API to read mail from code.

Does this work with Playwright or Selenium?

Yes. The core is a unique address, bounded polling and precise assertions, whatever the framework.
