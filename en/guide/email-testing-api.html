Temporary email API testing: polling, assertions and request budgets

A useful email test explains whether failure occurred in sending, waiting or checking the content. This guide gives a test design and request-budget example for your own regression workflow.

Published & updated 2026-10-04 · CleanTempMail product guide
IN THIS GUIDE01 / Identify each test run independently02 / Make waiting a bounded state machine03 / Assert that the message belongs to this flow04 / Count polls and extra operations separately05 / Plan CI secrets, cleanup and failure reports
01

Identify each test run independently

Create a unique run identifier and include it in the address prefix or subject. Parallel jobs cannot treat “there is a message” as success: they may find another run’s message.

Confirm the current domain and address workflow in the official Quickstart. The generator is optional; the documentation also describes composing an address locally on an active domain. Those choices have different request budgets.

02

Make waiting a bounded state machine

The message may not arrive at the exact moment your app sends it. Define both a poll interval and deadline, and look only for the current run’s message. For API errors, record the stage and status before deciding on a limited retry or termination according to the documentation.

# Workflow pseudocode, not an executable SDK
run_id = unique_id()
address = prepare_test_address(run_id)
trigger_your_app_email(address)
deadline = now() + wait_budget
while now() < deadline:
    messages = list_inbox(address)
    match = find_message(messages, run_id)
    if match:
        inspect_and_assert(match)
        cleanup_test_message(match)
        return success
    sleep(poll_interval)
return delivery_timeout

Endpoint paths, response fields and error mapping belong in an adapter based on the current API reference. An empty list is not a passed test, and waiting should not turn into an infinite retry loop.

When the deadline expires, use the missing email troubleshooting guide to separate sender failures from address, delivery and inbox issues.

03

Assert that the message belongs to this flow

  • Match the recipient, run ID and expected subject.
  • Check the fields your flow needs, not merely the presence of text.
  • Confirm a link’s hostname belongs to your test application before processing it.
  • Check the format and context of a verification code instead of mixing codes across runs.
  • For attachments, define checks for the name, type or content and budget additional requests.

Record the stage, duration and redacted assertion differences. Keep keys, complete verification codes and credential-bearing links out of logs.

04

Count polls and extra operations separately

Each protected inbox poll consumes quota, including an empty result. This example uses the optional generator, one message read and one deletion as three base operations. With a locally composed address, omit the generator request.

This assumes interval-based checks that stop at the limit. An immediate initial poll, retries, repeated reads or attachment downloads increase the budget. Stopping when a message arrives can reduce actual usage.

Adjust the run count and interval in the homepage quota estimator. Use the official API reference for billing rules.

05

Plan CI secrets, cleanup and failure reports

Keep an independent key in CI secret configuration and use it in a controlled server-side job, not public browser code, repositories, query parameters or logs. A shared trial key is not a dependable quota source for ongoing tests.

Report cleanup separately. If an assertion fails, preserve redacted evidence before cleaning up. If cleanup fails, record that state instead of treating delivered mail and successful cleanup as the same outcome.

Start with one welcome-message flow, then expand to password reset or attachment tests. Reuse the run identifier and stage reports across notification types so failures are easier to locate.
