How to Test Email OTP Codes: Expiry, Wrong Input and Resend Test Cases

Sending a 6-digit code by email looks simple, but the edge cases add up: expiry, wrong input, repeated requests, and whether old codes still work. Here is a checklist you can turn into tests, plus how to give each case its own temporary inbox.

Set up: one inbox per test case

The classic OTP testing bug is picking up another case’s code. Give each case its own address: CleanTempMail inboxes can be random or use a custom prefix, so put the case name or run ID in the prefix. For manual testing the web inbox is free with no sign-up, refreshes automatically (or manually) and shows message bodies.

For isolation in automation see isolated inboxes for parallel tests; for reading mail via API see the email testing API guide (the REST API uses paid one-time keys, with a shared ct-test key for trying it out).

02

Case 1: expired codes

  • Entering a code within its lifetime should succeed.
  • Entering the same code after expiry should say it expired, not just “wrong code”. Keep the two messages distinct.
  • Requesting a new code after expiry should deliver a fresh one that works.

The lifetime is whatever your product defines; read it from config rather than hard-coding it in tests.

03

Case 2: wrong input and attempt limits

  • One wrong entry should show an error and allow another try.
  • After the attempt limit you set, expect a lock or a forced new code; the exact policy is up to your requirements.
  • Wrong length, spaces or letters should be rejected gracefully.
04

Case 3: repeated sends and old codes

  • Click send twice: the inbox should hold two emails; compare the codes.
  • Verify your design: does the old code die immediately, or do both work? Either way the behaviour must be consistent and predictable.
  • Check the resend cooldown, see the resend verification email checklist.
05

Case 4: a code must not work twice

After a successful verification, submitting the same code again should be rejected. It is often forgotten, so add a replay step after every success case.

06

Debugging a missing code

  1. Confirm the recipient matches the form value exactly.
  2. Refresh the inbox manually once.
  3. When polling via API, log the number of empty polls; it separates “mail never arrived” from “did not wait long enough”.
  4. Still nothing? Follow the email not received guide.
07

Frequently asked questions

How do I test email verification codes?

Cover success within lifetime, expiry, wrong input, repeated wrong input, repeated sends, old-code invalidation and replay, using a separate inbox per case.

Do I need an account to test codes with CleanTempMail?

Not for manual use: the web inbox is free with no sign-up.

Why do I keep receiving another test’s code?

Share no inbox between cases; put the case name or run ID in the address prefix.

Can I fetch codes automatically?

Yes, CleanTempMail offers a paid REST API; see the email testing API guide.
