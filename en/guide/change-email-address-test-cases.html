How to Test Change-Email Flows: Test Cases for Updating a Login Email

Changing an email address is easy to get wrong: the new address takes effect before it is verified, the old address is never notified, or a taken address gives no warning. Testing the full flow needs two real inboxes, an old one and a new one. This checklist shows how to do it with two isolated temporary inboxes.

Setup: two separate inboxes

Create two CleanTempMail addresses: one as the old address to register the test account, one as the new address to receive the confirmation. Inboxes can be random or use a custom prefix, so put old and new in the prefix to tell them apart. The web inbox is free with no sign-up, refreshes automatically or manually, and shows message bodies and attachments.

To fetch mail in automation see the email testing API guide (the REST API uses paid one-time keys, with a shared ct-test key to try it); for signup itself see the signup verification test cases.

02

Case 1: verifying the new address

  1. Submit a new address while signed in and confirm the new inbox receives a confirmation email whose link targets the current environment.
  2. Before the link is clicked, the login email should still be the old one.
  3. After the click, the login email becomes the new address and signing in with it works.
03

Case 2: the old address and notifications

  • If your product notifies the old address of a change, check it arrives and reads clearly.
  • After the change, the old address should no longer work for sign-in or password recovery.
  • The number of emails is correct, with no duplicates.
04

Case 3: expiry, repeat clicks and stale links

  • The link stops working after its intended lifetime, with a clear message.
  • Clicking the same link twice should give a sensible message on the second click, not an error.
  • Submitting two different new addresses in a row: whether the first link is invalidated should match your rules. For resend behaviour see the resend verification email test cases.
05

Case 4: address already taken, and format issues

  • Entering an address used by another account should give a clear message without leaking what should stay private.
  • Try the current address, a malformed address, and the same address in different case, and check the results are consistent. See the duplicate email signup test cases for case handling.
06

Case 5: session and security

  • Whether the change asks for the password or another check should match your design.
  • While the link is unclicked, the rest of the account should work normally.
  • Emails should never contain a password or other secrets.
07

When the confirmation email does not arrive

  1. Confirm the address matches the new inbox exactly.
  2. Refresh the inbox manually once.
  3. When polling via API, log the number of empty polls to separate “never sent” from “did not wait long enough”.
  4. After the test, delete messages or clear the inbox to keep the next case clean.
08

Frequently asked questions

What should I test in a change-email feature?

New address verification, old address notification, link expiry and repeat clicks, taken addresses, format and case, and session and security behaviour.

Why use two temporary inboxes?

One acts as the old address that registers the account, the other receives the confirmation, so both ends of the flow are verified.

Do I need to sign up for CleanTempMail to test?

Not for manual use: the web inbox is free with no sign-up.

Can I fetch emails automatically?

Yes, CleanTempMail offers a paid REST API; see the email testing API guide.

Are emails kept permanently?

No, emails are temporary and not stored permanently.
