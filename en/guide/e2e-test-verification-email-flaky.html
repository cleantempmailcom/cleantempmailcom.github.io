E2E tests failing on verification emails? Waiting for mail reliably in Playwright

When a login or signup test fails only at the “enter the emailed code” step, the mail is rarely lost; the test is waiting the wrong way. Using Playwright as the example, this guide stabilises such tests with a unique address, a bounded poll and precise assertions.

Why verification-code tests turn flaky

There are only a few usual causes: a fixed sleep that is too short, so you read before the mail arrives; parallel jobs sharing one address and reading each other's mail; leftovers from a previous run mistaken for the current code; and a timeout that says nothing about whether the app never sent, the mail never arrived or the assertion is wrong.

All of them have one fix: make each run care only about its own message, and give the wait a clear upper bound.

02

Step 1: one unique address per run

The CleanTempMail web inbox is free and needs no registration, with random addresses and a custom prefix; to read mail from code, use the paid API. Put the run ID or test name in the prefix, for example e2e-login- plus a random string, and parallel jobs stop interfering.

Check the site for the currently available addresses and domains. If you need to control the domain, see the custom domain guide.

03

Step 2: bounded waiting with expect.poll

Playwright ships expect.poll, which re-runs a function at intervals until the assertion passes or times out. The sketch below is illustrative: fetchMessages is an adapter you write from the official API docs, so no endpoint path or field is assumed here:

import { test, expect } from '@playwright/test';

test('login with emailed code', async ({ page }) => {
  const address = makeAddress('e2e-login');   // unique, with a random suffix
  await page.goto('/login');
  await page.getByLabel('Email').fill(address);
  await page.getByRole('button', { name: 'Send code' }).click();

  const code = await expect.poll(async () => {
    const msgs = await fetchMessages(address); // your adapter
    const m = msgs.find(x => x.subject.includes('verification'));
    return m ? extractCode(m.body) : null;
  }, { timeout: 60_000, intervals: [2_000, 3_000, 5_000] })
    .not.toBeNull();
  // continue with the extracted code
});

Key points: state both the limit (60 seconds here) and the intervals; returning null means “not yet”, never “pass”. With the paid API every poll counts toward quota, empty results included, so do not make intervals too tight; see the API testing guide for budgeting.

04

Step 3: assert the message belongs to this run

  • The recipient equals the unique address generated for this run.
  • Subject or sender match expectations, not merely “a message exists”.
  • The code has the right format (length, characters) before it goes into the form.
  • For links, check that the hostname belongs to your test environment before visiting.

For signup flows, the verification email test-case checklist covers resend, duplicate signup and more.

05

Step 4: make a timeout explain itself

When the wait expires, report at least the stage (app trigger, waiting, parsing), time waited and how many messages the last poll returned. Keep full codes and credential-bearing links out of logs.

If the app did send and the inbox stays empty, work through the missing-email troubleshooting steps to separate sender, address and inbox problems before filing a bug.

06

Before moving to CI

  • Keep the API key in CI secret configuration, used only in server-side jobs, never in the repository, query strings or logs.
  • The shared trial key on the site is for trying things out, not a dependable quota for ongoing tests.
  • Delete the message when the test ends; on failure, save redacted evidence first.
  • Run these tests only against your own product and test environments; follow third-party sites' rules.
07

Frequently asked questions

Does this work with Cypress or Selenium?

Yes. The core is a unique address, a bounded poll and precise assertions, independent of framework; Playwright's expect.poll is just one way to write it.

Why not just sleep for ten seconds?

A fixed wait is either too short and flaky or too long and slows the pipeline. A bounded poll continues as soon as the mail arrives.

Can parallel tests read each other's mail?

Not if every run uses a unique address with a random suffix and asserts the recipient.

Does polling use quota?

With the paid API every poll counts toward quota, empty results included, so set sensible intervals and a limit.

Can I automate with the web inbox?

The web inbox suits manual checks. To read mail from code, use the site's API.
