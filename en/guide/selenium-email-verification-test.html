How to Test Email Verification Codes with Selenium

Selenium can click buttons and fill forms, but it cannot receive email. The verification code or confirmation link is often the flakiest step in a signup test. This guide gives a simple approach: one temporary inbox per test, wait for the email, read it, then bring the browser back into the flow.

Why Selenium needs separate email handling

Browser automation only sees the page. Where the verification email goes, when it arrives and what it says all happen outside it. A shared test mailbox leads to tests grabbing each other's emails, or old messages confusing the result.

A steadier pattern is one fresh address per test. With a unique address, the inbox only holds mail that test triggered. For running in parallel, see isolated inboxes for parallel tests.

02

The flow in five steps

  1. Prepare an address: at the start of each test, generate a random address (CleanTempMail supports random or custom prefixes and several domains).
  2. Fill the form with Selenium: enter the address in the signup form and submit.
  3. Wait for the email: poll the inbox in your test code until the target message appears or a timeout hits.
  4. Extract the code or link: read the body, and use a regex to pull out the code or the confirmation link.
  5. Return to the browser: type the code into the page, or have the driver open the link, then assert the outcome.

To read the inbox from code, use the CleanTempMail REST API (paid one-time keys; a shared ct-test key is available to try it). See the email testing API guide.

03

Waiting strategy: avoid fixed sleeps

  • Poll, do not sleep: check the inbox every few seconds and continue the moment the email arrives.
  • Set an overall timeout: fail the test on timeout and put the address and waited time in the error message.
  • Empty polls count: empty API polls count toward usage, so do not poll too aggressively.
  • Keep evidence on failure: save the address and a screenshot, then check the web inbox to see whether the email was really never sent.

More ideas for late emails are in testing delayed verification emails.

04

Extracting codes and links safely

  • Bound your regex: codes usually have a fixed number of digits; match exactly that many so you do not catch other numbers in the email.
  • Keep the link whole: confirmation links often carry long parameters; do not truncate or double-encode them.
  • Do not burn the link early: if a script visits a one-time link first, it may already be invalid; decide who opens it.
  • HTML vs plain text: check which format the body really is before choosing a parser.
05

Common Selenium pitfalls

  • Reusing addresses: two tests on one address mix their emails.
  • Double submits: clicking send twice produces two emails; be explicit about which one you assert on.
  • Slow CI: make timeouts more generous than on your laptop.
  • Rejected domains: if the system under test blocks some domains, switch to another CleanTempMail domain or use a custom domain (MX pointing to mail.cleantempmail.com).
06

FAQ

Can Selenium read email directly?

No. Selenium only drives the browser; read the inbox separately in test code, for example with the CleanTempMail REST API.

Should every test get a new address?

Yes, ideally. Separate addresses avoid cross-talk and make parallel runs easy.

Does the REST API cost money?

It uses one-time keys with quota plans; you can try it first with the shared ct-test key.

Does the web inbox need signup?

No. The web inbox is free with no signup and is handy for checking emails by hand.
