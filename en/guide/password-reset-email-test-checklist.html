How to Test Password Reset Emails: Expiry, One-Time Links and Repeat Requests

Forgot-password is easy to under-test and costly when it breaks: the email never arrives, a link works twice, or an expired link gives no hint. This checklist turns password reset mail into concrete test cases and shows how to receive each message in an isolated temporary inbox.

01

Why password reset deserves its own tests

Reset mail is tied to account security: a leaked or never-expiring link is a back door, and a missing email locks users out. It also differs from sign-up verification, because the account already exists, so repeat requests, invalidated old links and session handling all matter.

If you have no sign-up cases yet, start with the sign-up verification test checklist; both can share one test-address strategy.

02

Before you start: prepare isolated addresses

A reset needs an existing account, so register and verify with a fresh address first. CleanTempMail’s web inbox is free, needs no sign-up, and offers random addresses or a custom prefix. Put the case ID in the prefix (for example reset-001) so your results table matches the inbox.

Use one address per case and never reuse it, or an earlier reset email will contaminate the next check. For parallel runs see one temporary inbox per test case.

03

Eight core cases and what to assert

Password reset email test cases
ScenarioActionAssert
Normal resetClick “Forgot password” on a verified accountEmail arrives; recipient is correct; link points to the test environment, not production
Link worksOpen the link and set a new passwordReset page loads; new password signs in; old one no longer does
Single useClick the same link again after a successful resetRejected with a clear message, not the reset form again
Expired linkUse the link after its lifetimeRejected; user is told to request a new one; no technical details exposed
Repeat requestsRequest a reset twice in a rowMatches your design: only the newest link works, or both do; the rule is explicit and consistent
Unknown accountSubmit an address that never registeredResponse does not reveal whether the account exists; no reset email is sent
Rapid requestsSubmit many times in a short windowRate limit or cooldown applies; mail is not sent without limit
Email contentOpen the message bodyPlaceholders filled; no garbled text; no plaintext password; a “wasn’t you?” note

Lifetimes and cooldowns come from your own product design. Write “matches spec” with the actual number rather than borrowing a figure from elsewhere.

04

Four steps for a manual run

  1. Create the account. Register and verify with the test address; note the time.
  2. Trigger the reset. Request it in the app, then return to the web inbox and use auto or manual refresh.
  3. Check the message. Open the body and check recipient, subject, link domain and wording. CleanTempMail blocks external images in messages, so focus on text and links.
  4. Finish and clean up. Complete the reset, then test single use and expiry; finally delete the message or clear the inbox so no usable reset link lingers.

If the email never shows up, work through the troubleshooting steps before filing a bug.

05

When you automate it

For frequent regression you can script the flow. CleanTempMail’s paid REST API can read messages; follow the official docs for endpoints. Keep three rules:

  • Bound the wait. Poll at a fixed interval, then fail with the address and stage instead of retrying forever.
  • Match by address and subject. Accept only the message for this run, not “the latest one”.
  • Polls count toward quota. The site says protected requests are counted every time, including polls that return nothing, so avoid very tight intervals.

The API testing guide shows how to budget polling. The shared trial key is for trying things out; for continuous tests use your own key stored in CI secrets.

06

Pitfalls to avoid

  • Full links in logs. A reset link acts like a temporary password; keep only redacted snippets in reports.
  • Real users’ addresses. Use dedicated test addresses so real people never get your test mail.
  • Mail is temporary. The privacy notes on the official site say messages are not stored permanently, so save screenshots you need as evidence during the run.
Test only your own systems

These cases are for your product or an environment you are authorised to test. Do not fire bulk reset requests at accounts on third-party sites.

07

Frequently asked questions

How long should a password reset link last?

There is no universal answer; it depends on your security design. What matters in testing is that an expired link is rejected with a prompt to request a new one. Use the lifetime from your spec.

Why should an unknown email not say “not registered”?

An explicit message lets others probe which addresses have accounts. A common approach is to show the same neutral message for every input and only email real accounts. Follow your own product design.

Do I need an API to test reset emails?

Not necessarily. The web inbox is enough for manual regression; consider the paid API when the case must run often and automatically.

Does the test need an existing account?

Yes. A reset targets an existing account, so register and verify with a dedicated test address first, then request the reset.

Are reset emails kept in the inbox forever?

No. The official site says mail is temporary and not stored permanently; save any evidence you need during the test.
