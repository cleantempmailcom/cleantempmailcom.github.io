Custom-domain temporary email: MX setup, verification and testing

Decide which addresses should use temporary receiving before connecting your own domain. A separate mail domain for testing makes daily and test mail easier to distinguish. Use this planning and acceptance checklist alongside the current provider instructions.

01

Choose the mail domain you want to connect

If daily mail uses name@example.com, a proposed test address could be run123@qa.example.com. These are examples, not usable service domains. Replace them with a domain whose DNS you control.

Inspect existing MX records for the exact name and save the configuration. Do not repurpose a domain that currently receives business mail without planning the change. If you choose a subdomain, confirm that the current CleanTempMail setup flow supports that name before submitting it.

02

MX controls receiving for a mail domain

An MX record routes incoming mail. Its name corresponds to the domain after the address’s @; its target is a mail-server hostname rather than a web URL. Its priority helps order the candidate receiving servers.

Web records such as A, AAAA and CNAME serve a different purpose. Being able to open a website does not establish that the domain’s mail routing is correct.

Use the values shown by the provider

Get the MX target, priority and verification requirements from the current CleanTempMail setup screen. Apply those values to the mail domain you chose, keeping example names separate from your actual configuration.

03

Configure, verify, then test delivery

  1. Confirm control of the name and identify its existing mail service.
  2. Read the provider’s instructions for the required MX and verification values.
  3. Edit the correct DNS name and check whether your DNS panel appends the zone name.
  4. Submit the domain to CleanTempMail and complete verification.
  5. After verification, prepare an address for your test.
  6. Send a test from an account you control and record the result.

Follow the current official domain instructions. Seeing a DNS record and receiving a real message are separate checks.

04

Read the DNS result carefully

On a machine with dig, this query shows the example test domain’s MX records. A DNS query does not change records or send mail.

dig MX qa.example.com +short

Compare the returned targets and priorities with the setup requirements. An empty result calls for checking the name and zone. An older value calls for checking resolver caching and the authoritative DNS service the domain actually uses.

DNS panels differ in whether the name field expects qa or a complete domain. Follow the panel’s instructions so that the record does not accidentally become qa.example.com.example.com.

05

Record your acceptance checks and rollback plan

  • Save the before-and-after records, change time and responsible person.
  • Check that daily mail still follows its intended path.
  • Identify test messages with a unique subject or run ID.
  • Complete a send, receive, read and cleanup cycle.
  • If something fails, compare the original configuration and delivery logs before restoring records.

If DNS looks correct but mail is missing, use the delivery troubleshooting guide. DNS routing is not inbox access control or a promise of long-term message storage.

To repeat this acceptance check in your own app, follow the API email testing workflow and record a separate result for delivery, content checks and cleanup.
